# Deadline-aware source scheduling

Administrators can choose `scheduleMode: fixed | deadline_aware` in the research form or collection-policy API. Fixed is the default and continues to use cadenceHours. Omitted mode values preserve an existing setting. The configured fixed interval remains stored when adaptive mode is selected. A policy with no recorded adaptive history can become due on the next eligible scheduler pass, even if its old target was in the future. Disabled sources and Retry-After/review holds remain ineligible.

Deadline-aware mode evaluates published records for each source using their recorded ISO date-only deadlines. A deadline dated today through 14 UTC calendar days ahead selects a 24-hour scheduling interval. Today is included for collection priority, without changing the public catalogue’s conservative closing-today visibility rule. Otherwise the source uses a 168-hour interval, including sources with unknown deadlines or no currently near published record. Closed, rejected and draft records do not trigger daily priority; past dates do not either.

A future dated record can shorten the weekly target to midnight UTC at the start of its 14-day window. New or changed published facts can also advance a previously weekly plan once a daily interval has elapsed. The scheduler’s effective due calculation and operations due counter share one rule, so a stored target may be accelerated on a later pass. Existing due targets are not postponed when mode changes; the next processed pass sets the new interval.

Each eligible pass is bounded to 25 source policies and uses row locks/active-job uniqueness. It records last_scheduled_at and advances the target even if an active job prevents a duplicate insert, matching existing scheduling semantics. These are scheduling attempts, not proof of a fetch, successful review or publication verification. Worker/source/host gates still govern collection, and scheduling does not change opportunity details or verified_at. Permission review remains manual, including the existing enabled-policy save behavior that clears Retry-After after operator review.

The mode does not infer source deadline timestamps, source timezone, rolling deadlines or admission cutoffs. A recurring scheduler and worker still need qualification/deployment; there is no guarantee of exact execution time under backlog, pauses or holds. Official-source rechecks before notifications and source-to-publication freshness remain separate work. Migration 025 adds only private policy fields and a supporting published-record index; table count remains 40.
